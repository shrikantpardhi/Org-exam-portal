# Smart Competitive Examination Platform — Scope & Freeze Authority

**Version:** 1.5
**Date:** 7 October 2026

This file is the scope authority for the package. It defines what the platform is, what it is not, and which document governs when two documents appear to conflict.

---

## 1. Product boundary

**One organization per deployment.**

The platform runs for a single active organization at any time. There is one organization context for the running deployment.

The domain model, schema, and APIs are designed for this boundary. They are not designed as tenant-isolated SaaS infrastructure.

The platform does not include:

- a tenant-membership model
- tenant routing
- cross-tenant authorization
- tenant billing isolation
- tenant-specific academic partitioning
- a SaaS control plane
- tenant-aware reporting redesign
- tenant-scoped API contracts

Future compatibility is preserved at boundaries — for example, by passing organization context through service contracts rather than hard-coding a single organization identifier — but the current behavior and contracts remain single-organization.

## 3. What is deliberately not in scope

**Multi-tenant SaaS.** Future work.

**AI-driven capabilities.** Question generation, explanations, difficulty prediction, personalized recommendations, natural language search, and AI administration assistance remain future work. AI must never silently alter official examination data. AI-generated questions follow Draft → Review → Approved → Published.

**Advanced proctoring.** Browser lockdown, camera proctoring, AI cheating detection, biometric verification. Basic integrity controls (focus detection, session locking) are permitted as operational features but are not mandatory platform capabilities.

**Native mobile applications.** The platform is web-first and desktop/tablet-optimized.

**Payment provider-specific persistent structures.** The payment gateway is isolated behind an adapter boundary. Provider-specific data does not enter the domain schema.

## 4. Freeze rule

A specification change must not silently introduce:

- a new domain entity
- a new persistent table
- a new API family
- a new authorization architecture
- a new runtime model

When the schema, API, or domain model does not support a required behavior, the correct action is to record the need as a formal change, resolve it through a versioned decision, and reflect it everywhere it matters.

## 6. Engineering principle

**Do not over-engineer to solve a future problem.**

Build the single-organization product correctly. Preserve reproducibility and examination integrity. Keep multi-tenancy as a separately designed future expansion.

The platform is not "a website that conducts tests." It is a configurable examination engine with a web-based learning, assessment, commerce, analytics, and administration platform around it.

The architecture protects five things above everything else:

1. **Examination correctness**
2. **Data integrity**
3. **Historical reproducibility**
4. **Authorization correctness**
5. **Operational reliability**

Everything else is optimized around these foundations.

---

## 7. Freeze state

The package is frozen at the specification level. Implementation may proceed through all phases without pausing for unresolved schema, API, or design gaps.

Evidence tasks — the 5,000-user scale test, security regression, backup and restore, observability validation, final reconciliation — remain execution work. They close only when the corresponding tests execute and produce retained evidence.

Business-level workstreams — compliance, mobile UI, SMS and WhatsApp channels, pricing, go-to-market, support operations — remain outside the engineering package and proceed in parallel.
