# P7 load gate — v1.5.0-rc2 on the production-like environment

**Date:** 2026-10-23
**Candidate:** `v1.5.0-rc2` (annotated tag at `f07acfd`)
**Environment:** `infrastructure/environments/production-like` (co-resident, 24 logical cores, Docker VM 8 GB)
**Operator:** implementation agent
**Verdict:** **FAIL — the P7 §9 latency gate is not met.** Submission success, exam-failure, snapshot
integrity and reconciliation all pass. Latency fails at every step, and the 5,000-user step did not
produce a valid measurement.

> **This run does not authorise a GO.** The release decision stays **NO-GO**. Three harness defects were
> found and fixed, and one platform defect was found and fixed; the latency gate itself is untouched by
> any of them and still fails badly.

## 3. Latency at 5,000 users — the gate

P12 §9 requires **p95 < 100 ms** at 5,000 users for `attempt.start`, `attempt.questions`,
`attempt.response.save`, `attempt.submit`, `session.recover`.

**Result: FAIL.** No endpoint measured at 5,000 users is inside the gate, and the run is not even a
valid 5,000-user measurement.

### 3.1 Per-endpoint p95 (ms), by step

| Endpoint | 100 | 500 | 1,000 | 2,500 | 5,000 |
|---|---:|---:|---:|---:|---:|
| `attempt.start` | 1203.4 | 2523.6 | 2325.5 | 2062.0 | **1921.8** |
| `attempt.questions` | 1069.6 | 2107.7 | 1592.5 | 1431.8 | **1312.2** |
| `attempt.response.save` | 47.5 | 50.1 | 55.4 | 66.3 | **48.4** |
| `attempt.submit` | 36.4 | 52.1 | 33.1 | 176.5 | **41.8** |

| `auth.login` | 2304.0 | 4081.8 | 2743.9 | 1556.0 | **0.0 \*** |

\* `auth.login` p95 = 0 at 5,000 users is **not** a good result. It is the artefact of 4,786
connection-refused responses, which return fast (§5.1). The endpoint is unmeasured at 5,000 users.

**Three of the five gated endpoints fail at every step:**

| Gated endpoint | Required | Best observed | Verdict |
|---|---|---:|---|
| `attempt.start` | < 100 ms | 1203.4 ms @ 100 users | **FAIL** |
| `attempt.questions` | < 100 ms | 1069.6 ms @ 100 users | **FAIL** |
| `attempt.response.save` | < 100 ms | 47.5 ms @ 100 users | pass at ≤1,000 users only |
| `attempt.submit` | < 100 ms | 33.1 ms @ 1,000 users | pass except 2,500 |
| `session.recover` | < 100 ms | 44.6 ms @ 5,000 users | pass |

`attempt.start` and `attempt.questions` are **an order of magnitude** outside the gate at the smallest
step, and they do not improve with load — they are flat around 1–2.5 s, which is the signature of a
fixed cost rather than queueing contention.

### 3.2 Why the reported global p95 disagrees with the per-endpoint numbers

`load/k6/summary.js` reads `applicableLatency` from the **untagged** `http_req_duration` metric, so it
aggregates all eight endpoints together. At 100 users the slow trio
(`auth.login`, `attempt.start`, `attempt.questions`) is only **1.0 %** of 29,688 requests:

| Endpoint | n | p95 (ms) |
|---|---:|---:|
| `response.save` | 14,259 | 47.5 |
| `attempt.read` | 14,259 | 42.4 |
| `session.recover` | 679 | 47.1 |
| `attempt.start` | 100 | 1203.4 |
| `auth.login` | 100 | 2304.0 |
| `attempt.questions` | 97 | 1069.6 |
| `attempt.submit` | 97 | 36.4 |
| `response.list` | 97 | 52.2 |

The global p95 is therefore dominated by the 99 % that are fast. **The global figure (48.6–91.5 ms)
must not be quoted as the gate result**; the gate is per endpoint, and per endpoint it fails.

## 5. Defects found during this run

### 5.1 The 5,000-user step is not a valid measurement (harness, blocking for the gate)

The 5,000-user step produced **4,786 connection-refused** responses in its first ~2 seconds:

```
20:45:47 level=warning msg="Request Failed"
  error="Post \"http://localhost:8090/api/v1/auth/login\": dial tcp 127.0.0.1:8090:
          connectex: No connection could be made because the target machine actively refused it."
```

Refused counts scale with VU count and all occur in the first second of each step:

| Step | connection-refused |
|---:|---:|
| 100 | 0 |
| 500 | 245 |
| 1,000 | 791 |
| 2,500 | 2,285 |
| 5,000 | 4,786 |

Cause: the edge publishes `listen 80;` with **no `backlog=` argument**, so the listen queue is capped
at the kernel default (`somaxconn` = 4096 in the container). 5,000 VUs opening their first connection
in the same second overrun it, and the excess is refused rather than queued. The consequences:

- Only **214** of 5,000 students actually started an attempt (214 × `attempt.start` vs 5,000
  `auth.login`), so the 5,000-user latency figures describe **~4 % of the intended population**.
- `auth.login` p50/p95 collapse to 0 because refused sockets return immediately.
- The 5,000-user numbers in §3.1 are reported for completeness but **must not be read as a
  5,000-user gate result.** The gate fails regardless, on the smaller and fully valid steps.

Not fixed in this run: it needs a decision on the edge listen backlog (a `backlog=` argument on the
shared `listen` directive, or an OS-level `somaxconn` raise) and a re-run. It is recorded as GAP-160.

### 5.2 The evaluation worker never ran — platform defect, fixed

The `EVALUATION` handoff was correct: 992 jobs were queued, each carrying the published `answerKeyId`.
None were ever claimed. Two independent causes:

1. **`EVALUATION_WORKER_ENABLED` defaulted to `false`** (`application.yml`) and was never overridden in
   the production-like environment. The default dates from GAP-071, when the handoff carried no key;
   GAP-071 is closed but the default was never revisited.
2. **`EvaluationWorker` bypassed `JobStateService`.** It called `jobRepository.claim(...)` directly from
   a `@Scheduled` method, which has no transaction, so every tick threw
   `TransactionRequiredException: No EntityManager with actual transaction available for current
   thread`. `JobStateService` exists precisely to wrap those `@Modifying` transitions, and its javadoc
   describes this exact failure; every other worker (`ReportWorker`, `AnalyticsWorker`, the
   communication workers) already used it. The evaluation worker was the only one that did not.

Fixed: the worker now routes claim/complete/fail through `JobStateService`, the environment sets
`EVALUATION_WORKER_ENABLED=true`, and `EvaluationWorkerTest` asserts the transactional route so the
direct-repository call cannot come back. After redeploy all **992 jobs completed with 0 failures**
(992 `CALCULATED` results). Recorded as GAP-161.

### 5.3 `load/seed.mjs` could not produce a working environment — harness, fixed

Three defects, each of which made a fresh environment unusable:

- **No administrator.** `LoadCohortProvisioningService` only ever grants `STUDENT`, and
  `ADMIN_ROLE_ASSIGN` is deliberately ungranted to every role (V3, ADR-0014, GAP-116), so a fresh
  database has **no administrator at all**. The harness used to insert the role directly; that was
  removed in `e4c008e`. Every ADMIN call then failed `403 Access denied`. Fixed by restoring an
  explicit, idempotent `grantCorpusRoles()` in `seed.mjs`. Recorded as GAP-159.
- **No answer key.** `seed.mjs` never published one, so evaluation had nothing to score against and
  every submitted attempt stayed un-evaluated. Fixed with `load/publish-answer-key.mjs`, which resolves
  `correct_option_id` from `question_option.is_correct` (AGENTS.md rule 19) and refuses to publish a
  partial key.
- **Staff in the ramp population.** `build-credentials.mjs` fell back to
  `manifest.studentPassword` for any email missing from `studentCredentials`, so the corpus author and
  reviewer — who are `STUDENT` members with prepared attempts — received **another account's
  password**. Being first in schedule order they were the first two logins, which is the
  `BAD_CREDENTIALS` seen in the smoke run. Fixed by restricting the cohort to the student list.

Also fixed: `scripts/p7/reconcile.sql` used bare `:schedule_id` for UUIDs, so psql substituted them
unquoted and **every** invocation failed with `trailing syntax error ... trailing junk after numeric
literal`. All UUID substitutions are now quoted (`:'schedule_id'`). The script had never actually run.

attempt that was actually started is missing questions (verified: non-FAILED attempts with ≠ 100
questions = **0**). So this is not Start Exam writing snapshot rows — it is the expected residue of two
failed preparation jobs, and the gate's query cannot distinguish the two cases. It should exclude
`snapshot_status = 'FAILED'`; recorded as a reconciliation-script defect, not a platform failure.

Those two attempts were never part of the ramp cohort: 10,004 prepared, 9,100 needed, 10,002 READY, so
the surplus absorbed them. The ramp consumed 793 + 200 = 993 attempts.

created no job. It was evaluated explicitly via `POST /attempts/{id}/evaluate` (the endpoint
`15-P6 §26` provides for exactly this case), which is why `submitted_without_result` is now PASS. This
is the smoke test, not a ramp client; it is excluded from the ramp population.

`published = 0` in both schedules: results are `CALCULATED`. Publication is a separate operator action
(`POST /results/{id}/publish`), and the gate does not require it. Recorded for completeness.

## 8. Gaps closed and opened

**Closed**
- GAP-161 (new) — evaluation worker never claimed a job: `EVALUATION_WORKER_ENABLED` defaulted false
  and the worker bypassed `JobStateService`, throwing on every tick. Fixed, tested, verified (992/992).
- GAP-159 (new) — `seed.mjs` could not grant the roles a fresh database needs (no ADMIN since
  `e4c008e`). Fixed and verified.
- Answer-key omission and staff-in-cohort in the load harness; `reconcile.sql` UUID substitution. Fixed.

**Opened**
- GAP-160 — edge listen backlog: `listen 80` has no `backlog=`, so ≥500 concurrent first connections
  overflow the queue and are refused. This invalidates the 5,000-user latency measurement and must be
  fixed before the gate can be assessed at 5,000.
- GAP-162 — `scripts/p7/reconcile.sql` `start_burst_zero_new_rows` does not exclude
  `snapshot_status = 'FAILED'`, so preparation failures are reported as Start-Exam snapshot writes.
- GAP-163 — `load/k6/summary.js` reports `applicableLatency` from the untagged `http_req_duration`
  metric, mixing all eight endpoints; the global p95 masks per-endpoint gate breaches.

**Existing, still open and now confirmed as the dominant cost**
- GAP-130 (Residual) — `attempt.start` / `attempt.questions` are 1.1–2.5 s p95 against a 100 ms gate.
  bcrypt login and snapshot materialisation remain the structural cost. **The GAP-156 and GAP-059 fixes
  did not move these endpoints into the gate.** GAP-059 trimmed the start path but `attempt.start` is
  still 1203 ms at 100 users.

## 9. What must happen before a re-run

1. **Fix the edge listen backlog (GAP-160)** and prove the 5,000-user step completes with zero
   connection refusals. Without this there is no 5,000-user measurement.
2. **Fix the two harness reporting defects (GAP-162, GAP-163)** so the gate is judged per endpoint and
   integrity is not polluted by known-failed rows.
3. **Then address the actual latency (GAP-130).** `attempt.start` and `attempt.questions` need an
   order-of-magnitude improvement — from ~1.2 s to < 100 ms at 100 users — before any step can pass.
   Nothing in this run suggests the current architecture is close.
4. Re-run with `EVALUATION_WORKER_ENABLED=true` (already set in this environment) so submission →
   evaluation completes inside the measured window.

The release decision remains **NO-GO**.

```bash

  P7_RELEASE=v1.5.0-rc2 P7_ENVIRONMENT=production-like-co-resident \
```
