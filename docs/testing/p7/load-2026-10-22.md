# P7 load-test evidence — 2026-10-22

First executed load run for the P7 workloads (`specs/16-P7-Pilot-V1.5.md` §24–§36) and the P12
performance gate (`specs/21-P12-Hardening-V1.5.md` §9, §56–§60).

Every number below was read from k6 summaries and the ramp runner's evidence file. A `—` means the metric
was not produced by that run, never that it was zero.

> **Outcome: the ramp ran to completion and the integrity gate passed at every step; the latency gate
> failed at every step.** This closes GAP-084 (generator capacity) and closes the *measurement* half of
> GAP-130, but it does **not** close GAP-130: the p95 gate was measured and missed. The release decision
> stays **NO-GO**.

## 4. Workload

Profile F (`mixed`) — the realistic blend used for the capacity claim (§32):

- authenticate as a distinct synthetic student;
- start the exam;
- read the attempt and the full 100-question snapshot;
- answer with per-question ETag autosave, 3 s think time, ~1 in 7 marked for review;
- ~1 in 20 reconnects mid-exam (session recovery);
- read all responses, then submit.

The distribution is **synthetic and documented as such** (§32): no pilot traffic data exists.

Ramp per P7 §33 (100 → 500 → 1,000 → 2,000 → 3,000 → 4,000 → 5,000), one shared-iterations pass per
step, disjoint `(student, schedule)` cohort per step. No manual data mutation occurred between steps.

**The seven §33 steps were executed as two invocations**, because each ramp consumes a disjoint cohort
and the total requirement is `100+500+1,000+2,000+3,000+4,000+5,000 = 15,600` fresh
`(student, schedule)` pairs while the dataset holds 12,633:

1. `--steps=100,500,1000,2500,5000` (9,100 pairs) — the 2,500 step was from an earlier provisional
   progression and is reported below as an extra row.
2. `--steps=2000,3000,4000` (9,000 pairs) — the remaining §33 steps, after rebuilding credentials from
   the then-unconsumed pairs.

Between the two invocations **no data was mutated by hand**: the only change is that step 1's students
had submitted, which is the workload's own effect. The credential manifest was rebuilt from the database
so step 2 used students who had genuinely never started.

## 8. Failures identified

**F1 — `attempt.questions` is the dominant latency cost: a per-question N+1 in the read path.**

The frozen read returns the entire 100-question snapshot in one 110 KB payload. The SQL for the snapshot
rows executes in **0.08 ms**, and a single session read takes **90–104 ms** — so the cost is in the
application layer, not the database.

Root cause, located in `AttemptQueryService.questions` → `toView`: the snapshot rows and options are
batched correctly, but `toView` calls `contentCatalog.runtimeQuestion(...)` **once per question**. Each of
those calls (`ContentCatalogService.runtimeQuestion`) performs four separate lookups — question version,
question, template, and the version's options — and re-renders every option's content through
`renderer.render(...)`. A 100-question snapshot therefore issues roughly **400 queries and 400 LaTeX
renders per read**, for content that is immutable and identical on every request.

The cost grows with concurrency: p95 rises from 1,591 ms at 100 users to 3,410 ms at 5,000. This endpoint
is above the p95 gate even at the smallest step.

This is a genuine platform finding, not a harness artefact: the harness issues exactly the frozen
`GET /attempts/{attemptId}/questions` call the reference client issues.

**F2 — `attempt.start` degrades superlinearly with concurrency.**

p95 rises 415 ms → 3,107 ms as users go 100 → 5,000. The underlying queries are sub-millisecond
(`EXPLAIN ANALYZE`: 0.19 ms for the attempt-question count, 0.09 ms for the attempt lookup), so the cost
is application-side work in the start path, amplified by contention.

**F3 — the p95 gate fails at every step, including 100 users.**

There is no step in the §33 progression where the applicable-endpoint p95 is under 100 ms. The gate
cannot be passed on this host with the current implementation, regardless of the ramp step chosen.

**F4 — a full stack restart loses in-flight snapshot preparation.**

During dataset construction the whole stack restarted once (host memory pressure: 0.3 GB free of
15.7 GB). One attempt was left `FAILED` and required an explicit reset to `PENDING`; the reclaim path
(`reclaimStale`) only covers `PREPARING`, not `FAILED`. There is no exposed endpoint to trigger
`retryFailed`, so an operator must intervene. This is an operational finding, not a throughput one.

## 9. What the harness proved about itself

The harness was validated before its numbers were trusted, and four of its own bugs were found and fixed
during this run; they are recorded because each one would have produced a wrong number:

1. **Per-question ETags.** One ETag variable was reused across questions, so 43.8% of saves returned
   `412` and the run looked like a platform failure. Fixed: ETags are tracked per question.
2. **One exam per iteration.** `constant-vus` restarted a *fresh* exam each loop, so a 60-second run with
   500 VUs produced 6,591 logins instead of 500 and the concurrency number was meaningless. Fixed: every
   profile uses `shared-iterations` with exactly `P7_USERS` iterations.
3. **Cohort selection.** Deriving the student offset from a count of consumed attempts overlapped
   already-started students (the consumed set is not a contiguous prefix), producing 55–100% spurious
   exam failures. Fixed: the credential manifest is built from attempts that are genuinely `NOT_STARTED`
   and `READY`.
4. **Readiness scope.** Requiring *every* attempt in the database to be `READY` blocked a run whose own
   cohort was prepared. Fixed: the check is scoped to the cohorts the run consumes.

Additional validation:

- **Generator capacity** was measured independently (`load/k6/capacity-probe.js`, no server traffic):
  2,500 and 5,000 concurrent VUs for 30 s each with **0 interrupted iterations**, 149,785 iterations at
  5,000 VUs. The generator is not the limiting factor at these steps.
- **Absent data stays absent.** Metrics a profile did not produce are `null` in the summaries.
- **Thresholds are per profile**, so an empty `submission_success_rate` cannot fail a start burst.

## 10. Reprojection: what a production-like run would need

This run cannot be promoted to a capacity claim, and GAP-130 must not be closed on it. To close it:

1. A production-like topology (separate load-generation host, dedicated database, real edge) per P7 §12
   and P12 §56.
2. An immutably tagged release candidate and pinned container digests (GAP-083).
3. The two hot endpoints addressed first — F1 and F2 — because the gate fails at 100 users, so no amount
   of extra infrastructure headroom changes the verdict without an implementation change.
4. PostgreSQL tuned for a 1.4M-row snapshot table set (`shared_buffers = 128 MB` is far below the
   1,019 MB `attempt_question_option` working set).

## 11. Known limitations (stated, not implied)

1. **Single co-resident host.** Generator and target shared 24 cores and 15.7 GB RAM. The generator was
   proven capable of 5,000 VUs, but CPU and memory were shared, so the target's measured latencies include
   generator contention.
2. **Backend targeted directly** (`:8080`). The Nginx edge and its TLS/HTTP path were not in the measured
   path. Edge latency therefore is not represented in these numbers.
3. **Synthetic workload.** Profile F is a documented synthetic distribution, not pilot traffic (§32).
4. **Pool and worker tuning above production defaults.** `DB_POOL_MAX_SIZE=25` (default 10) and the
   dataset-build worker settings differ from production; the workload phase ran with the delivery worker
   disabled. A production deployment would have background workers competing for the same resources.
5. **Not an availability measurement.** A finite run cannot establish 99.9% annual availability
   (P12 §59).
6. **Candidate not immutably tagged** (GAP-083), so this is not a frozen build artefact.
7. **Host memory pressure.** The host reached 0.3 GB free during dataset construction and restarted the
   stack once. The measurement runs themselves completed without restart.
