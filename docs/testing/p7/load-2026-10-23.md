# P7 load re-run — GAP-156 verification

**Date:** 2026-10-23
**Candidate:** `27fa543` (the GAP-156 batching commit on top of `v1.5.0-rc1` / `c966d1c`)
**Environment:** `local-docker-single-host` — Docker Desktop 29.8.2, 8 GB VM, 24-core / 15.71 GB host,
PostgreSQL 16 via PgBouncer, k6 v2.2.0
**Profile:** F `mixed` (P7 §32), 100 questions per attempt, 100 concurrent VUs
**Result:** the questions endpoint improved 56% and **is no longer the bottleneck**. The p95 gate still
fails, now on `auth.login`. **GAP-130 remains Residual, not Closed.**

---

## 1. Why this run exists

GAP-130 recorded a failed P7 §33 ramp on 2026-10-22: p95 155.1 / 352.6 / 475.5 / 552.6 / 395.0 / 516.4 /
430.3 ms across 100 → 5,000 users against a < 100 ms target, with `attempt.questions` at 3,534 ms p95 at
2,000 users identified as the dominant term.

GAP-156 then removed the per-question N+1 in that endpoint (309 → 10 SQL statements, 84 → 27 ms on a
single-session 100-question read). This run measures what that fix did under load, and establishes
whether GAP-130 can close.

## 2. What was measured

The P7 `mixed` profile at 100 users, against commit `27fa543`, on the same host and harness as the
2026-10-22 run. The 100-user step is directly comparable because it was executed in both runs.

| Metric (100 users) | Before (`c966d1c`) | After (`27fa543`) | Change |
|---|---|---|---|
| `attempt.questions` p50 | 1,210.0 ms | 652.7 ms | **−46%** |
| `attempt.questions` p95 | **1,962.4 ms** | **861.1 ms** | **−56%** |
| `auth.login` p95 | 911.2 ms | 1,240.4 ms | +36% |
| `attempt.start` p95 | 345.5 ms | 935.3 ms | +171% |
| `attempt.read` p95 | 92.9 ms | 64.8 ms | −30% |
| `response.save` p95 | 109.1 ms | 66.6 ms | −39% |
| Gateway p95 (all requests) | 332.4 ms | 368.5 ms | +11% |

Integrity in the after-run was clean: 100/100 submissions, 0.00% exam failure, 0.00% HTTP failure,
`snapshotDelta` exactly `+0/+0` (no snapshot materialized during the burst, P7 §27).

## 3. What this proves, and what it does not

**Proven.** The batching works under concurrency, not just in the single-session unit measurement. The
questions endpoint's p95 dropped by more than half and it has stopped being the dominant cost. `attempt.read`
and `response.save` — the high-volume paths — also improved 30–39%, which is consistent with the endpoint
no longer monopolising connection-pool slots.

**Not proven — and this is the honest finding.** The p95 gate still fails, and the reason has moved. At 100
users the largest single term is now `auth.login` at 1,240 ms p95, followed by `attempt.start` at 935 ms.
Neither is caused by GAP-156.

The login cost is structural: `SecurityConfig.passwordEncoder()` returns
`PasswordEncoderFactories.createDelegatingPasswordEncoder()`, i.e. bcrypt at the default strength 10. A
bcrypt verification is *deliberately* tens of milliseconds of CPU; that is the point of the algorithm.
Under 100 concurrent logins on an 8 GB VM the CPU saturates and each request queues behind others. This is
a capacity/architecture question (login endpoint hardening, a faster encoder for synthetic cohorts, or
genuinely more CPU), not a query-count question, and it is out of scope for GAP-156.

`attempt.start` at 935 ms is consistent with the same saturation: the start path itself performs a bounded
~7 reads and has no N+1 of the kind GAP-156 addressed.

## 4. Ramp progress and why it stopped at the first step

The ramp runner stops at the first threshold breach rather than escalating (P7 §33: "stop and diagnose
rather than blindly escalating"). It stopped at 100 users. Continuing to 500 / 1,000 / 2,500 / 5,000 would
not have produced new information about GAP-156 — the endpoint under investigation had already improved and
was already not the bottleneck — and would have taken hours against a login bottleneck that dominates
regardless of cohort size.

This is a deliberate limitation of this evidence, recorded rather than glossed: **the full seven-step ramp
was not re-run.** The 2,000-user comparison from 2026-10-22 (where `attempt.questions` was 3,534 ms p95)
therefore has no after-value.

## 5. Dataset notes

- Cohorts were drawn from 17,169 READY, not-yet-started (student, schedule) pairs on the real 100-question
  assessment version `e6f8260e…`, more than the 9,100 the seven-step ramp needs.
- Six additional schedules were created through the frozen HTTP contract and prepared by the platform's own
  worker, not by direct SQL.
- 5,000 student credentials were re-issued through `LoadCohortCli` (the GAP-085 mechanism), because the
  previous manifest's hashes no longer matched.
- The credential manifest was rebuilt to contain only pairs that are genuinely startable. An earlier
  attempt built it from all (student, schedule) pairs including already-submitted ones, which produced a
  100% exam-failure rate — a harness-data error, not a product defect, and it is why the first two re-runs
  in this session produced no usable numbers.
- The snapshot-preparation worker was disabled during measurement so that background preparation of
  unrelated schedules could not be mistaken for Start Exam materializing a snapshot (P7 §27). The first
  re-run was invalidated by exactly that false positive (`attempt_question +19,700`) and was discarded.

## 6. Conclusion

GAP-156's fix is confirmed beneficial under load: the questions endpoint's p95 fell 56% and it is no longer
the bottleneck. GAP-130 does **not** close. The p95 gate still fails, and the dominant term is now
`auth.login`, a bcrypt-cost and CPU-capacity problem that this change neither caused nor addressed.
